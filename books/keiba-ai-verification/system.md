結論を疑うにはまず、疑う価値のあるデータが要ります。この章はシステム構成の話です。読み飛ばしても本筋は追えますが、後の章で出てくる障害（文字コード移行、レート制限、サイレント障害）の舞台装置でもあります。

## 全体構成

- **収集**: Python + BeautifulSoup。netkeiba のレース結果・払戻・血統・オッズをスクレイピング
- **保存**: SQLite 1ファイル（races / race_results / payouts / pedigree / odds_history など9テーブル、約112MB）
- **自動化**: GitHub Actions。月曜に週次収集、木〜日に予測とメール通知、金土日に発走前オッズのスナップショット
- **モデル**: LightGBM（lambdarank）。147特徴量、オッズ・人気は特徴量から除外
- **予測配信**: SMTP でメール通知。重賞の前日予測と当日予測

規模感は次の通りです。

| 項目 | 値 |
|---|---|
| レース数 | 18,777（2020〜2026年） |
| 出走結果 | 約25.7万行 |
| 払戻レコード | 約22.5万行 |
| 年間レース数 | 約3,450（JRA全場） |

## 地味に効いた設計判断

**1. 払戻テーブルを「検算装置」として使う**

単勝の確定オッズと払戻には `オッズ × 100 = 払戻金額` という恒等式が成り立ちます。これを品質チェックに常設したことが、後の章で出てくる「オッズ汚染」の発見につながりました。**独立に収集した2つのデータ系列の間に成り立つはずの恒等式は、最強のデータ検証器です**。

**2. 外部基準との突き合わせ**

「JRAは年間約3,400レース、1開催日24〜36レース」という外部知識と件数を照合するチェックを入れています。これで「2022〜2024年の札幌・函館・福島・新潟が丸ごと欠けている（全体の28%）」という系統的欠落を発見しました。収集システムは自分が集めていないものを報告できないので、**完全性の検証には外部の物差しが必須**です。

**3. レート制限の実測**

netkeiba は1日約7,000リクエストでIPブロック（HTTP 400、解除まで数時間〜半日）されることを2回の事故で実測しました。以後、大量収集は1日5,000件以内・リクエスト間隔1.2秒以上に制限しています。スクレイピングで作るシステムは、この種の「怒られの閾値」を運用パラメータとして持つ必要があります。

## データリーク防止を収集層に埋め込む

予測系MLで最初に壊れるのはここです。「レースXを予測する特徴量は、レースXより前の情報だけから作る」を、特徴量生成のSQLレベルで強制しました。

```sql
SELECT rr.* FROM race_results rr
JOIN races r ON rr.race_id = r.race_id
WHERE r.date < ?  -- 予測対象レースの開催日より厳密に前
```

「訓練データとテストデータを期間で分ける」だけでは不十分です。騎手の勝率、種牡馬の成績、馬の過去走 — **集計系特徴量の一つ一つが、それぞれカットオフ日を守る必要があります**。この徹底が甘かった時期に何が起きたかは、第4章で数字つきでお見せします。
