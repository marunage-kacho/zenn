趣味で競馬の予測AIを作っています。毎週土曜に血統データを取りに行くバッチがあって、CIは毎回緑。ログにも「完了」と出ている。だから動いていると思っていました。

ある日ふと最終更新日を見たら、1月で止まっていた。7ヶ月前です。

今年出走した馬の4頭に1頭、血統が空のまま学習に使われていました。

## 何が起きていたか

原因は、保存先のカラム名とスクレイパーが返すキー名が微妙に違っていたことでした。`horse_id` と `horseId` みたいな、そういう話です。

問題はそこではなく、そのエラーの扱い方でした。こういうコードになっていました。

```python
success = 0
failed = 0
for horse in horses:
    try:
        data = scrape(horse)
        save(data)
        success += 1
    except Exception:
        failed += 1

logger.info(f"完了: 成功 {success} / 失敗 {failed}")
```

毎回エラーは出ていたんです。でも `except` で握り潰して、件数だけ数えていた。そしてその件数を、誰も見ていなかった。

ジョブは落ちない。終了コードは0。CIは緑。HTTPは200。それでも中身は7ヶ月ずっと空でした。

## 気づいたきっかけ

予測の精度が妙に安定しないので、学習データを眺めていたときです。血統の特徴量が欠損している行がやけに多い。

そこで初めて「このデータ、最後に更新されたのいつだ？」と確認しました。

```sql
SELECT MAX(updated_at) FROM horse_pedigree;
-- 2026-01-22
```

血の気が引きました。

## 直したこと

3つです。

**1. エラーは件数ではなく中身を出す**

```python
except Exception as e:
    failed += 1
    logger.error(f"失敗: horse_id={horse.id} {type(e).__name__}: {e}")
```

当たり前の話なんですが、やっていませんでした。件数だけ見ていると「まあ何件か失敗することもあるよね」で流してしまう。実際の例外メッセージが出ていれば、KeyError が毎行出ていることに1週間で気づけたはずです。

**2. データの「鮮度」を毎週見る**

収集処理とは別に、鮮度だけを見るチェックを足しました。

```python
last = fetch_max_updated_at()
age_days = (datetime.now() - last).days
if age_days > 10:
    raise RuntimeError(f"データが {age_days} 日古い（最終更新 {last}）")
```

処理が成功したかどうかではなく、結果として保存されたデータが新しいかどうかを見る。ここが分かれ目でした。

**3. 収穫ゼロならジョブを赤くする**

```python
if success == 0:
    sys.exit(1)
```

1行です。これを書いていれば、7ヶ月ではなく1週間で止まっていました。

## 何を学んだか

「落ちてない」と「動いている」は別物でした。

監視で見ていたのは、ジョブが落ちていないことと、終了コードが0であることと、HTTPが200であることでした。全部グリーンです。でもそれは「処理が走ったこと」の証明であって、「意味のある結果が出たこと」の証明ではなかった。

これ以来、失敗より沈黙のほうが怖くなりました。落ちてくれれば気づけますが、黙っていると気づけない。

本業でも監視の仕組みは見るのですが、同じ目で見るようになりました。アラートが鳴っていないことを「問題がない」の根拠にしていないか、というところです。

## おまけ: 似た罠

この件のあと、他のバッチも見直しました。似たパターンが2つありました。

- リトライ回数の上限を書いていなくて、接続できないまま延々とリトライし続けるスクリプト。ノートPCの電池が切れるまで気づきませんでした
- 平均値だけ見ていた監視。平均は60%で余裕に見えて、実際はピークの5分だけ100%に張り付いていた

どれも「見ている数字が、知りたいことを表していなかった」という同じ形です。

自分で作ったものだと、つい「ちゃんと作ったから大丈夫」と思ってしまう。実際には、ちゃんと作ったかどうかより、壊れたときに気づけるかどうかのほうが効きました。
